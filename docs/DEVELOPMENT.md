# Development and contract updates

## Frozen tools

Build with Go1.27.2 and Node24.19.0. `go.mod`, `go.sum` and `web/package-lock.json` are the dependency authorities. Actual SQLite kernel3.53.4 is queried before WAL; module-version numbers are not treated as SQLite-version evidence.

OpenAPI3.0.3 is generated by `tools/generate_openapi.py`; TypeScript types use locked openapi-typescript7.13.0. Go uses explicit wire DTOs and production request schema checks. Unknown fields, duplicate JSON keys, invalidUTF-8, extra JSON, invalid query parameters and out-of-bounds values are rejected.

## Contract change sequence

1. Update business DTOs/behavior and corresponding generator schemas/operation fields.
2. Run `python tools/generate_openapi.py`.
3. In web, run `npm exec -- openapi-typescript ../api/openapi.json -o src/generated/api.ts`.
4. Add/change real HTTP fixtures for behavior and schema; validate required/nullable/enum/status/envelopes.
5. Run `python tools/check_contract.py`, frontend tests/build and affected Go checks.

The drift checker works without Git and leaves generated files for inspection on mismatch. TypeScript compilation does not prove runtime responses; real HTTP fixture comparisons provide that check. Formats not implemented by the schema checker are not claimed as fully validated.

## Build and package

Build the frontend **before** the Go application, since web/dist is embedded at Go compilation. `tools/package_release.py` creates a public source-input manifest, builds Linux/Windows binaries with that hash, copies notices, packages launchers and computes checksums. It never copies a workspace DB/key/log, dependency cache, private design or paid evaluation output.

The manifest excludes generated verification records and compiled frontend assets, which have separate hashes in build metadata; their source inputs remain included. Source archive SHA-256 and source-input SHA-256 are different concepts and both are recorded.

Source ZIP includes the compiled frontend for offline inspection; rebuilding from a fresh checkout still starts with npm ci/build. Use `-buildvcs=false` for source archives without Git metadata. Windows is cross-compiled locally; native checks are a separate gate.

## Verification tools

- `go test -race -timeout 180s ./...`: behavior, concurrency, fault injection and contract fixtures.
- `npm test --prefix web`: DOM/transport/interaction tests in jsdom.
- `python tools/smoke_release.py --binary build/flowdesk --out build/smoke.json`: real process and HTTP loop.
- `go run -buildvcs=false ./cmd/flowdesk-eval --mode plan --plan full`: no network or fees.
- `go run -buildvcs=false ./cmd/flowdesk-bench --out build/bench.json`: isolated fictional dataset, real HTTP, explicit timed workload.
- `python tools/audit_release.py --release-dir build/release`: allowlist, hashes, versions, embedded assets and secret/file boundaries.

GitHub Actions configuration prepares Linux race and Windows native suites. It is not itself evidence that those runners passed. There are no provider calls, deployments, publish actions or credential uploads in default CI.


## Personal workspace and UI regression checks

The personal launcher uses --workspace with an independent directory. --workspace --init-admin is an offline setup alternative. Existing schema1 workspaces do not migrate or reseed.

After building, run tools/smoke_workspace.py --binary build/flowdesk --out new-workspace-check.json. It uses fictional own accounts and a local fake provider through the real live dispatch path, including tool calls and missing-consent rejection; it never establishes real model quality.

Optional browser QA uses Playwright and tools/smoke_browser.cjs --binary build/flowdesk --out new-browser-check.json. An existing module may be passed using --playwright-module; custom Chromium uses --chromium-executable and optional --args-module. Browser files and screenshots stay in a private QA directory, outside release inputs.
